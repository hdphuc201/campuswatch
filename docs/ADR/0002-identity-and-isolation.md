# ADR-0002: CampusWatch identity, device tokens, and per-user isolation

- **Status:** Accepted
- **Date:** 2026-11-11
- **Phase:** P2 (implementation plan, sections 8, 9, 11, and 13)

## Context

Many students share one Backend. User A must never read, change, or receive anything that
belongs to User B (plan section 3). The extension needs two kinds of credentials: one for
the student (account and settings) and one for the browser that collects data (probes now,
snapshot ingest in P5). These are CampusWatch credentials only; Portal credentials never
reach the Backend (ADR-0001).

## Decision

### Accounts and sessions

- Email and password. Emails are stored trimmed and lowercased (enforced by a database
  check). Passwords are hashed with argon2id (19 MiB, 2 iterations, 1 lane; OWASP minimum).
  Unknown emails and wrong passwords return the same response after the same amount of work.
- **Access token:** HS256 JWT signed with `AUTH_SECRET`, 15 minutes by default. It carries
  the user id and the session family id. Every request also checks that the family is still
  active, so logout takes effect immediately.
- **Refresh token:** 256-bit random value (`cwr_…`), 30 days by default, stored only as a
  SHA-256 hash. Each refresh token works once and is rotated within its family. Replaying a
  used token revokes the whole family (theft detection).
- Email verification and password recovery are deferred until an email provider is chosen.
  `users.email_verified_at` exists for that.

### Devices

- `POST /devices/register` (user token) returns a 256-bit device token (`cwd_…`) exactly
  once; only its SHA-256 hash is stored. Revoking a device stops its token immediately.
- Device tokens are accepted only on routes marked `@DeviceAuth()` and act for the device's
  owner. User tokens are not accepted on device routes, and device tokens are not accepted
  on user routes.

### Isolation (three layers, plan section 9)

1. **Database:** every user-owned table references `users(id)` with `ON DELETE CASCADE`;
   one connection per user and adapter (`UNIQUE (user_id, adapter_key)`).
2. **Server-side scope:** a global, default-deny guard authenticates every route unless it is
   marked `@Public()`. The owner id comes only from the verified token. Request bodies are
   strict Zod objects, so fields like `userId` are rejected. Every query on user-owned data
   filters by that owner id; another user's resource returns 404, the same as a missing one.
3. **Tests:** `apps/api/test/isolation.int.test.ts` exercises User A/User B access with user
   and device tokens against a real PostgreSQL database in CI. Removing an owner filter makes
   it fail (checked by temporarily deleting the filter).

PostgreSQL row-level security can be added later as an extra layer; it does not replace the
checks above.

### Persistence

Drizzle ORM 0.45 with `pg`. SQL migrations are generated by drizzle-kit, reviewed, committed
under `apps/api/drizzle/`, and applied explicitly with `pnpm db:migrate`, never at startup.
CI fails when the schema and the committed migrations disagree.

## Endpoints (P2)

| Method and path                      | Auth   | Purpose                                         |
| ------------------------------------ | ------ | ----------------------------------------------- |
| `GET /health`, `GET /health/ready`   | public | Liveness; readiness including the database      |
| `POST /auth/register`                | public | Create an account; returns tokens               |
| `POST /auth/login`                   | public | Returns tokens                                  |
| `POST /auth/refresh`                 | public | Rotate a refresh token                          |
| `POST /auth/logout`                  | public | Revoke the refresh token's session family (204) |
| `GET /auth/me`                       | user   | Current profile                                 |
| `POST /devices/register`             | user   | Register the extension; returns a device token  |
| `GET /devices`                       | user   | Active devices                                  |
| `DELETE /devices/:id`                | user   | Revoke a device (204)                           |
| `POST /portal-connections`           | user   | Record consent and create a connection          |
| `GET /portal-connections`            | user   | The caller's connections                        |
| `DELETE /portal-connections/:id`     | user   | Disconnect and record consent revocation (204)  |
| `POST /portal-connections/:id/probe` | device | Report the Portal session state                 |

A new connection starts as `LOGIN_REQUIRED` and becomes `CONNECTED`, `LOGIN_REQUIRED`, or
`PORTAL_UNAVAILABLE` from probe reports.

## Consequences

- No Portal secret and no CampusWatch token is stored in plain text.
- Every authenticated request costs one indexed database lookup (session family or device).
- Rate limiting for login, refresh, and probes is not implemented yet (P7). It must be in
  place before the pilot (plan section 11).
- `AUTH_SECRET` rotation invalidates all access tokens (refresh tokens keep working). Key
  rotation with multiple active keys can be added if needed.
